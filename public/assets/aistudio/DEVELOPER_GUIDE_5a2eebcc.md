# Developer Guide — Chess Opening Trainer

*This guide is the law for anyone working on this project. It is designed to force a junior to think like a senior: **no code without a plan, no plan without assumptions, no merge without proof.***

---

## 0. Read This First

### 0.1 What This App Is

Chess Opening Trainer is a static, browser-only app that helps a player memorize a chess opening:

1. **Pick** an opening (e.g., Queen's Gambit) from the library.
2. **Study** its variations, with the moves played out on a board.
3. **Drill** — the app plays the opponent's moves from the file, you play yours, and it tells you when you get it wrong.

- **Platform:** static site on GitHub Pages. Desktop + mobile browsers (support matrix in Section 6.C.4).
- **Stack:** vanilla HTML/CSS/JS as ES modules, [chess.js](https://github.com/jhlywa/chess.js) for move legality. No framework, no backend, no build step.
- **Content:** openings are Markdown files in `/lines/`, governed by the format spec in Section 2.

### 0.2 Non-Goals (Read Before You Scope Anything)

We are explicitly NOT building these. If your task seems to require one, stop and propose it on the roadmap (Section 5.1) instead of building around it:

- No backend, no accounts, no login, no server-side anything.
- No engine evaluation — no Stockfish, no "best move" hints. The opponent plays moves from the file, nothing else.
- No multiplayer, no sharing, no comments.
- No native app, no Electron, no PWA install flow.
- No user-generated content stored anywhere — openings are files in `/lines/`, reviewed like code.

Non-goals are what stop scope creep. Changing one is a change to this guide (Section 13), not a quiet decision inside a task.

### 0.3 The Golden Rule

> **We don't write code to figure out what to build. We write a plan to figure out what to build, then we write code to execute the plan.**

If you can't explain a task in 1 page, you are not ready to code it.

Every task follows the same 4 phases, no exceptions:

**1. PLAN → 2. BUILD → 3. PROVE → 4. SHIP**

Section 5 expands these into 7 concrete steps: steps 1–3 are PLAN, step 4 is BUILD, step 5 is PROVE, steps 6–7 are SHIP. Same process, more detail.

You do all of your thinking inside the `/work` folder (Section 4).

## 1. Architecture — How the App Fits Together

You cannot plan a task if you don't know what owns what. Here is the map.

### 1.1 File Layout

```
/                          → site root (what GitHub Pages deploys)
  index.html               → the only page. Loads style.css + app.js (type="module"), holds the import map.
  style.css                → all styling. Mobile-first.
  app.js                   → app shell: owns the single state object, fetches files, wires events, switches screens.
  parser.js                → PURE. Markdown text → data. No DOM, no fetch, no chess.js.
  validate.js              → PURE. Parsed data + chess.js → errors[] (move legality, format checks).
  board.js                 → draws a position (FEN) onto a DOM-grid board. No game logic.
  drill.js                 → the drill loop state machine: user move → check → opponent reply → feedback.
  ui.js                    → tiny DOM helpers. ALL text insertion via textContent — never innerHTML (Section 6.A.7).
  /vendor/chess.mjs        → chess.js, vendored at a pinned version (Section 7.3). The only runtime dependency.
  /lines/                  → content: one .md file per opening (Section 2).
  /tests/                  → Node test files, run by `npm test`.
  /scripts/                → dev scripts (e.g., validate-content.mjs).
  manifest.json            → GENERATED by GitHub Actions (Section 1.5). Never hand-edit.
  DEVELOPER_GUIDE.md       → this file.
  ROADMAP.md               → the task list. The only source of task IDs (Section 5.1).
  README.md                → how to run, how to add an opening, how to deploy.
  /docs/OPENING_FORMAT.md  → the content contract, copy of record (Section 2).
  /work/                   → per-task planning + proof, committed to git (Section 4).
```

New files are not free: every file you create must appear in your PLAN's "Files I Will Touch".

### 1.2 Module Responsibilities

| Module | Owns | Must never do |
|---|---|---|
| `parser.js` | text → `{ formatVersion, title, playerColor, variations[], errors[] }` | touch the DOM, fetch, import chess.js |
| `validate.js` | parsed data → `errors[]`, using chess.js for legality | touch the DOM |
| `board.js` | render a FEN as a board | decide whose turn it is or what moves mean |
| `drill.js` | the drill state machine | parse files, fetch, own the global state |
| `app.js` | global state object, event wiring, screen switching | contain parsing/validation/rendering logic |
| `ui.js` | DOM helpers (text via textContent) | contain feature logic |

If a function seems to need two columns at once, the design is wrong — split it, or route it through `app.js`.

### 1.3 Data Flow

```
/lines/queens-gambit.md
      │  fetch() (app.js)
      ▼
parser.js   → raw data { title, playerColor, variations[], errors[] }
      │
      ▼
validate.js (chess.js) → move legality checked, errors[] merged
      │
      ▼
app.js (state) → ui.js renders variation list → board.js draws position
      │
      ▼
drill.js: user move → legal? → opponent's reply from the file → repeat
```

### 1.4 State Management

One source of truth: a single `state` object owned by `app.js`. No scattered booleans across files.

- State changes only through named transition functions (`goToDrill`, `applyUserMove`), never by reaching into the object from wherever.
- Any task with more than 3 states MUST include a state transition table in its PLAN (Section 12). If you can't write the table, you don't understand the feature yet — which means you're not ready to code it.

### 1.5 What `manifest.json` Is

A static host can't list a directory, so a GitHub Actions workflow regenerates `manifest.json` — the list of files in `/lines/` — whenever `/lines/` changes. `app.js` fetches this manifest to build the opening library. Rules:

- It is a generated file: never hand-edit it, never review it like code.
- You may commit it once so local dev works; merge conflicts in it are resolved by regenerating, not by hand.

## 2. The Content Contract — Opening File Format

**This is the most important spec in the repo.** `parser.js`, `validate.js`, and every file in `/lines/` must agree on it. The copy of record is `/docs/OPENING_FORMAT.md`; this section mirrors it. If they ever disagree, `/docs/OPENING_FORMAT.md` wins — fix the other the same day.

Any change to the format must bump `formatVersion` and either stay backward-compatible or migrate every file in `/lines/` in the same PR.

### 2.1 Anatomy of an Opening File

````markdown
---
formatVersion: 1
title: Queen's Gambit
playerColor: white
---

## Notes
Optional free text, 1–3 sentences, shown above the variation list.

## Variation: Queen's Gambit Declined, Orthodox
playerColor: black
```moves
d4 d5
c4 e6
Nf3 Nf6
```

## Variation: Queen's Gambit Accepted
```moves
d4 d5
c4 dxc4
```
````

### 2.2 Rules

1. **Frontmatter (required):** `formatVersion` (integer), `title` (string), `playerColor` (`white` or `black`).
2. **`playerColor` is lowercase** — `white` / `black`, exactly. The parser does NOT silently lowercase; a bad value is an error in `errors[]`, not a warning. Typo protection beats convenience.
3. **One variation per `## Variation: <name>` heading.** The name is required and must be unique within the file.
4. A variation may override `playerColor`; if absent, it inherits the file-level value.
5. **Moves live in a `moves` fenced code block:** SAN only, space-separated, **no move numbers** (`1.` is forbidden), no comments, no NAGs, no annotations.
6. Whitespace is insignificant — lines inside a moves block may wrap freely.
7. **Limits:** max 20 variations per file, max 40 plies per variation. This keeps the UI and the drill loop sane. Need more? Split the file, or reopen this spec via PR.
8. UTF-8 encoding, LF line endings. Filename: kebab-case named after the opening (`queens-gambit.md`, `sicilian-najdorf.md`).

### 2.3 Error Policy

- Unknown frontmatter key → error (typo protection), never silently ignored.
- Missing or illegal move → error naming the variation and ply: `Queen's Gambit Declined, Orthodox: move 7 (e5) is not legal`.
- The parser never throws. All problems come back as data in `errors[]`, and the UI decides how to show them. The app must never crash on bad content (Section 6.A.3).

### 2.4 Content Validation Gate

Every file in `/lines/` must pass `npm run validate-content` before merge, and CI enforces it. Content is code: a broken opening file is a user-facing bug.

When you start a task, create this folder. It is NOT shipped to users, but it IS committed to git so we can review your thinking.

```
/work/
  /task-1-2-parser/

    ASSUMPTIONS.md
    NOTES.md

  /task-1-3-board/
    PLAN.md
    ASSUMPTIONS.md

  /task-3-1-drill/
    ...
```

**Rules for `/work`:**

1. One folder per task, named after the ROADMAP task ID: `task-1-2-parser`. IDs come from `ROADMAP.md` — never invent one.
2. Never put real app code in `/work`. Real code goes where Section 1.1 says it goes. `/work` is for thinking, plans, and proof.
3. You cannot start coding until `PLAN.md` and `ASSUMPTIONS.md` are written AND reviewed (the review is recorded in PLAN.md §7).
4. You cannot mark a task done until `TEST-REPORT.md` is filled — with pasted command output, not just checkboxes.
5. Screenshots: compress to ≤200 KB each and commit under the task folder, or paste into the PR description. Never commit full-resolution captures — `/work` lives in git forever.

### What Goes In Each File

#### 1. `PLAN.md` — How You Are Going To Do It

Written **before** you write a single line of code. It must answer these 7 questions:

```markdown
# PLAN - Task 1.2: Parser

## 1. Goal
In one sentence, what does DONE look like?

## 2. Inputs & Outputs
What goes in? What comes out? Use the exact contract and cite it.
Example: Input = raw Markdown string (format per /docs/OPENING_FORMAT.md §2).
Output = { formatVersion, title, playerColor, variations[], errors[] }

## 3. Steps
List the steps in order. No code, just logic.
1. Split file on \n
2. Track state: FRONTMATTER -> META -> NOTES -> MOVES
3. ...

If your Steps section is longer than ~15 lines, your task is too big. Split it.

## 3b. State Table (ONLY for stateful tasks — see Section 1.4)
| From | Event | To | Side effects |
|------|-------|----|--------------|

## 4. Files I Will Touch
- Create: parser.js
- Edit: app.js (only to import)
- Will NOT touch: style.css, index.html

## 5. Edge Cases I Will Handle
- Empty file
- Missing `moves` block
- Illegal move

## 6. How I Will Prove It Works
- Unit tests in /tests/parser.test.js, run by npm test
- Manual test with queens-gambit.md on desktop + real phone

## 7. Review (filled in at Step 3 of the workflow)
- Reviewed by / date / verdict:
- Changes requested / resolved:
```

#### 2. `ASSUMPTIONS.md` — What You Are Guessing

This is the most important file. Seniors write this down. Juniors keep it in their head and forget it.

Every assumption must be in this format:

```markdown
# ASSUMPTIONS - Task 1.2: Parser

| # | Assumption | Why I Made It | What Happens If It's Wrong |
|---|------------|---------------|----------------------------|
| A1 | playerColor values are always lowercase white/black | OPENING_FORMAT.md §2.2 rule 2 | Parser reports an error naming the file and key — it does not silently lowercase |
| A2 | Moves blocks never contain move numbers | OPENING_FORMAT.md §2.2 rule 5 | Parser treats `1.` as a move token; validation fails — the error message must say "move numbers are not allowed" |
| A3 | chess.js is importable as the vendored module /vendor/chess.mjs | Architecture, Section 1.1 | Import fails at load time — fix the import map / vendor path, never work around it inside parser code |
| A4 | One file = max 20 variations | OPENING_FORMAT.md §2.2 rule 7 | validate.js enforces the limit with a clear error — we do not add pagination ad hoc |
```

**Rule:** If you make an assumption while coding and it's not in this file, STOP. Add it to the file first, then continue coding. This prevents "I thought you meant..." bugs.

**Cap:** more than ~10 assumptions means the task itself is underspecified — go back to the roadmap and split it.

#### 3. `NOTES.md` — Decisions & Dead Ends

Write down what you tried and why you rejected it. This saves the next person 2 hours.

```markdown
# NOTES - Task 1.2

- Tried using `marked` library. Rejected: It gives HTML, we need data. Too heavy.
- Tried regex to parse whole file at once. Rejected: Unreadable. Switched to line-by-line state machine.
- Decision: Use `line.trim()` on every line. This means leading spaces don't matter.
```

#### 4. `TEST-REPORT.md` — Proof, Not Promises

You cannot say "it works". You must show it. Automated tests without pasted output are not proof; manual tests without screenshots are not proof (Section 6.C.3).

````markdown
# TEST-REPORT - Task 1.2

## Automated Tests
- Command: `npm test` — paste the FULL output below. A checkbox without output is not proof.

```
> 17 tests, 17 passed, 0 failed
> ok 1 - parser: inherits playerColor from frontmatter
> ok 2 - parser: variation-level playerColor overrides file-level
> ok 3 - parser: illegal move lands in errors[], nothing thrown
> ...
```

- Command: `npm run validate-content` (if content or parser changed) — paste output.

## Manual Tests (Live URL)
- URL: https://username.github.io/repo-name
- Tested on: Chrome Desktop, Firefox Desktop, iOS Safari (real phone)
- [x] Load queens-gambit.md, 4 variations show — screenshot: screenshots/variations-mobile.png
- [x] Bad file shows a readable error, doesn't crash the app — screenshot: screenshots/bad-file.png

## Console Log
- Paste console output, or write: "0 errors, 0 warnings on desktop + phone"
````

## 5. The Workflow — Step by Step for Each Task

Steps 1–3 = PLAN, step 4 = BUILD, step 5 = PROVE, steps 6–7 = SHIP (Section 0.3).

### 5.1 The Steps

**Step 0: Pick the task off the roadmap.**
Tasks live in `ROADMAP.md` — the only source of task IDs. Each roadmap entry has: an ID (`1.2-parser`), a one-line goal, acceptance criteria, and dependencies. Never invent a task; if one is missing, propose it on the roadmap first, get it agreed, then start. Sketch of what entries look like (your real `ROADMAP.md` replaces this):

```markdown
| ID | Goal | Acceptance criteria | Depends on |
|----|------|---------------------|------------|
| 1.1-scaffold | Repo skeleton, dev server, CI | npm test runs green; Pages shows the page | — |
| 1.2-parser | Markdown → data per OPENING_FORMAT.md | Happy path + broken-path tests pass | 1.1 |
| 1.3-board | Render a FEN to the DOM board | Board matches for 10 known FENs | 1.1 |
| 3.1-drill | Drill loop with opponent replies | Full drill completes; wrong move flagged | 1.2, 1.3 |
```

**Step 1: Create the work folder.**
```bash
mkdir -p work/task-1-2-parser
```

**Step 2: Write PLAN.md + ASSUMPTIONS.md.**
Spend 30–45 minutes. No code yet. Ask: What are my inputs? What are my states? What are my edge cases? What am I assuming?

**Step 3: Get the PLAN reviewed, and record it.**
Ask another dev — or AI plus your own pass through the Section 9 checklist. The question to ask: "What did I miss? Which assumption is risky?" Fill in PLAN.md §7 (reviewer, date, verdict, changes requested). An unrecorded review did not happen.

**Step 4: BUILD.**
Create branch `task-1-2-parser`. Write code following Section 6. Keep functions small. Keep constants at the top. No magic numbers.

**Step 5: PROVE.**
Fill `TEST-REPORT.md`: pasted `npm test` output, `npm run validate-content` if content changed, manual tests on desktop + a real phone, console clean, screenshots.

**Step 6: SHIP.**
Open a PR using the Section 8 template, linking `/work/task-1-2-parser/PLAN.md`. CI must be green. Merge only after review (Section 9).

**Step 7: WRAP UP.**
Make `/work` match what actually shipped (plans drift during build — fix them), update the ROADMAP status, final pass on NOTES.md. Your `/work` folder stays in git; it is the project's decision history. Do not delete it.

### 5.2 When You're Stuck — Escalation Rules

- Genuine stuck-ness gets a **45-minute timebox**. (Stuck means "no new ideas to try", not "this is tedious".)
- Then: write the blocker in `NOTES.md` under **Questions For Reviewer** — what you tried, what happened, what you expected — and ask.
- Never silently change scope. Never quietly build a different feature. Never spin for 3 hours on your own.
- Being stuck is information, not failure. A written blocker unblocks the next person too.

### 5.3 AI Usage Policy

AI can draft, explain, and review. It is never the author of record:

- You must be able to explain every line you merge. If you can't, you're not done.
- AI-generated code goes through the same tests, review, and proof as human code. "The AI wrote it" is not a defense in review.
- An AI plan review counts only if its main objections and your responses are pasted into PLAN.md §7.
- Any dependency an AI suggests still goes through Section 7.3. AI hallucinates packages — verify a package exists and is maintained before installing anything.

## 6. Best Practices — The Senior Checklist

Apply this to EVERY task, even a 5-line change.

### A. Code Best Practices

**1. One Function, One Job.**
Bad: `doEverything()` that parses, validates, AND renders.
Good: `parseOpeningMarkdown()` returns data, `renderVariations()` takes data and shows UI, `validateMoves()` takes moves and returns errors.

**2. Pure Functions First.**
Your parser must be pure: same input string → same output object, every time. No `document.getElementById` inside `parser.js`. No `fetch` inside `parser.js`. This is what makes it testable in Node.

**3. Never Crash On Bad Data.**
This is a content app. Users will write bad Markdown. Your code must NEVER do this:

```js
// BAD — crashes the whole app
variations[0].moves[0]
```

Always do this:

```js
// GOOD — fails gracefully
if (!variations.length) return showError("No variations found");
if (!variation.moves?.length) return showError("Variation has no moves");
```

**4. No Magic Numbers.**
Bad: `setTimeout(..., 300)`.
Good: at the top of the file: `const OPPONENT_DELAY_MS = 700; const LOOP_DELAY_MS = 1500;` Then use the constant. Change it in one place.

**5. No Magic Strings.**
Bad: `if (state === 'USER_TURN')` scattered across 10 files.
Good: `const STATES = { IDLE: 'IDLE', USER_TURN: 'USER_TURN' }` in one place — and only `drill.js` may hold drill states (Section 1.4).

**6. Comment The WHY, Not The WHAT.**
Bad: `// Loop through lines`.
Good: `// We parse line-by-line, not with one big regex, because variations can be any length`.

**7. Never Trust Content — No innerHTML, Ever.**
This app parses Markdown written by humans and renders it. The moment someone writes `innerHTML` with parsed content, an opening file becomes an XSS attack.

```js
// BAD — attack vector: <img src=x onerror=...> inside an opening file
el.innerHTML = variation.name;

// GOOD
el.textContent = variation.name;
```

If you ever genuinely need HTML (you almost never do), sanitize it with DOMPurify and justify it in NOTES.md.

**8. Every Screen Has Three States.**
Every screen that loads or computes anything has loading, empty, and error states — designed, not accidental. User-facing errors say what happened and what to do next:

```js
// BAD
showError(String(err));

// GOOD
showError("queens-gambit.md has no `moves` block — see /docs/OPENING_FORMAT.md §2.2");
```

Raw stack traces are for the console, never for users.

**9. Accessibility Is Not Optional.**
A chess board is an accessibility minefield. Every UI task includes:

- Keyboard-only operation: a full drill must be playable with the keyboard alone.
- Visible focus on every interactive element (never `outline: none` without a replacement).
- ARIA labels for squares and pieces ("e4, white pawn").
- Highlights that don't rely on color alone (border/pattern + color).
- Touch targets ≥ 44×44 px; nothing hover-only (mobile has no hover).
- Respect `prefers-reduced-motion` for animations.

Accessibility is checked in the Definition of Done (Section 8) and in review (Section 9).

**10. One State Object, Explicit Transitions.**
Section 1.4 is the law: single state object, named transition functions, and a state table in the PLAN for stateful tasks. Twelve booleans scattered across files is the classic junior bug factory.

### B. Git Best Practices

**1. One Task = One Branch = One PR.**
Never work on `main` directly. Never mix two tasks in one branch. The branch name is `task-` + the roadmap ID with dashes:

```bash
git checkout -b task-1-2-parser
# ... work ...
git push origin task-1-2-parser
# Open PR, get review, squash-merge, delete the branch
```

**2. Commit Messages That Explain Why.**
Format: `type(scope): what + why`. The scope is the roadmap task ID as-is (branch = `task-` + ID with dashes; commit scope = the ID):

```
feat(1.2-parser): add inheritance for playerColor

File-level playerColor was not applied to variations without an
override, so all variations defaulted to white. Covers A1 in
/work/task-1-2-parser/ASSUMPTIONS.md.
```

Types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.

**3. Small PRs.**
A reviewer should get through your PR in 15 minutes. If it's more than ~400 changed lines or touches two tasks, split it. Commits stay small too — a commit is one logical change, not a day of work.

**4. Never Commit Secrets or Generated Files.**
`manifest.json` is generated (Section 1.5) — never hand-edit it. Never commit API keys, tokens, or credentials. If one leaks, rotate it immediately; deleting the commit is not enough.

### C. Testing Best Practices

**1. Test The Parser, Not The UI.**
UI is hard to test. Parser and validator are easy. 80% of your tests should target `parser.js` and `validate.js`. If the data layer is correct, UI bugs are easy to find.

**2. Test The Happy Path AND The Broken Path.**
For every task, at least 2 tests:
- Happy: correct file → correct output.
- Broken: bad file → graceful error, no crash.

**3. Reproducible Tests Only.**
Tests live in `/tests/` and run with `npm test` (Node's built-in test runner — zero extra dependencies). "I ran it in the console" is not a test: nobody else can re-run it, and it can't gate a merge. TEST-REPORT.md must paste the actual `npm test` output. Screenshots prove UI; they never replace tests.

**4. Manual Test On Real Devices.**
Before you mark a task done, test on:

- Desktop: Chrome, Firefox, and Safari — latest 2 versions each.
- Mobile: iOS Safari and Android Chrome on a real phone, not a devtools resize.

Browser support = last 2 versions of Chrome / Firefox / Safari, plus iOS Safari and Android Chrome. No IE, no legacy Edge. Chess boards break on mobile. You must test it.

**5. Console Must Be Clean.**
Zero errors, zero warnings in the console before you ship. If you see a warning and think "it's fine", it's not fine. Fix it, or document why it's unfixable in `NOTES.md`.

### D. Documentation Best Practices

**1. Update The Plan If You Change The Plan.**
If you discover during Task 1.2 that the Markdown format needs to change, you do NOT just change the code. You:
1. Update `/docs/OPENING_FORMAT.md` and bump `formatVersion` (Section 2).
2. Update `PLAN.md` and `ASSUMPTIONS.md` in `/work`.
3. Update the example files in `/lines/`.
4. Migrate every affected content file in the same PR.
Then change the code. Code and docs must never drift.

**2. README Must Stay True.**
Your `README.md` must always have: how to run locally, how to add a new opening, how to deploy. If a junior can't follow it in 5 minutes, it's wrong.

## 7. Tooling & Quality Gates

### 7.1 `package.json` — Dev-Only, No Build Step

```json
{
  "private": true,
  "type": "module",
  "scripts": {
    "test": "node --test tests/",
    "lint": "eslint .",
    "format": "prettier --write .",
    "validate-content": "node scripts/validate-content.mjs"
  }
}
```

ESLint + Prettier configs live in the repo and run in CI. "Small functions, no magic numbers, clean console" are enforced by tooling where possible — not by hope. An `.editorconfig` sits in the repo root (UTF-8, LF, 2 spaces).

### 7.2 CI — `.github/workflows/ci.yml`

Runs on every PR. All three gates must pass before merge — this is what turns "no merge without proof" from a suggestion into a rule:

```yaml
name: CI
on: [pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run validate-content
```

### 7.3 Dependency Policy

- **One runtime dependency: chess.js**, vendored into `/vendor/chess.mjs` at an exact pinned version. No runtime CDN — a CDN outage or a compromised package becomes a production incident the moment it happens. (If remote loading is ever unavoidable: pin the exact version + SRI hash and document the fallback in NOTES.md.)
- Pin exact versions everywhere (no `^`, no `~`).
- Every new dependency (dev included) needs a NOTES.md entry: what it's for, its size, its license, and why the built-in isn't enough. Licenses: MIT / Apache / BSD only.
- Zero-dependency by default. The best dependency is the one you don't have.

### 7.4 Deploy & Rollback

- `main` deploys to GitHub Pages on merge, via the workflow that also regenerates `manifest.json`.
- **Verify the live site after every merge:** open the deployed URL, load one opening, run one drill. Green CI proves the code, not the deploy.
- **Rollback = `git revert` on main + push.** Pages redeploys the previous state in minutes. Reverting is always allowed and always fast — never "fix forward" a broken site under pressure.
- **Cache busting:** browsers cache aggressively. When `app.js` / `style.css` behavior changes materially, bump a query string (`app.js?v=2`) or rename the file.

## 8. Definition of Done + PR Template

A task is done when ALL of these are true. A filled TEST-REPORT is necessary, not sufficient.

## 9. Code Review — What a Reviewer Actually Checks

Approval means: "I checked these and they're true." If you can't check one, say so instead of approving.

1. Does the code do what PLAN.md says — no more, no less? Scope creep kills reviews.
2. Are the ASSUMPTIONS still true after seeing the code?
3. Error paths: what happens with empty, broken, or oversized input? Where is the broken-path test?
4. Purity held: `parser.js` / `validate.js` touch no DOM and no fetch?
5. Magic numbers or strings? Constants at the top of the file?
6. Any `innerHTML` fed with parsed content? Instant block, no discussion.
7. New dependency justified per Section 7.3?
8. Would a dev understand this in 6 months? Do the comments explain WHY?

**SLA:** first review within 1 working day; the author responds to every comment (fix it or explain why not); re-review after fixes.

**Solo on this repo?** You still don't self-merge silently. Walk the Section 9 checklist with an AI as the reviewer, paste its objections and your responses into the PR, then merge. The record matters more than the headcount.

## 10. Content Pipeline — Openings Are Code

- Anyone can propose an opening file via PR. The PLAN is small (the contract already exists — Section 2 is your spec), but the flow is the same: PLAN → BUILD → PROVE → SHIP.
- Every content PR passes `npm run validate-content`. CI enforces it.
- **Content review = play every variation in the drill before approving.** "It parsed fine" ≠ "the opening is correct."
- A new opening needs: legal moves (chess.js-verified), correct per-variation `playerColor`, and variation names a human can read.
- A user reporting a bad opening file is a P1 bug — same severity as a crash, because to that user it is one.

## 11. The Junior → Senior Mindset Shift

| Junior Thinks | Senior Does |
| :--- | :--- |
| "I'll figure it out while coding" | "I'll figure it out in PLAN.md, then code" |
| "It works on my machine" | "It works on desktop + mobile, console clean, TEST-REPORT filled" |
| "I assume the file is correct" | "I assume the file is broken; I handle errors and write ASSUMPTIONS.md" |
| "I'll remember why I did this" | "I write it in NOTES.md so future-me remembers" |
| "Big PR, I'll explain later" | "Small PR, one task, plan attached" |
| "Comments explain what code does" | "Comments explain why we chose this approach" |
| "It parsed fine" | "It validated, AND I played every variation through" |
| "The AI wrote it and it looks right" | "I can explain every line I merged" |
